# EMS-Pro 大数据模块强化方案

面向毕业论文评审：强化 Hive 数仓分层建模 + MapReduce 分布式计算，构建「员工效能多维度分析」核心模块。

---

## 一、现状诊断（基于全量代码扫描）

| 编号 | 问题 | 证据位置 | 风险等级 |
| --- | --- | --- | --- |
| 1 | MapReduce 是单机模拟，不是分布式计算 | `bigdata/analysis/MapReduceDemo.java` 全文使用 `HashMap`/`Stream`，`pom.xml` 无 `hadoop-mapreduce-client-core` 依赖 | 高 |
| 2 | 数仓无分层，仅一张表 | `HiveRealService.createEmployeeTable()` 只建 `dim_employee` 一张表，命名 dim 实为事实快照 | 高 |
| 3 | 无行为事实表，算不出「效能」 | `schema-mysql.sql` 中 `employee` 仅静态属性（薪资/年龄/入职日期），无考勤、任务、绩效数据 | 高 |
| 4 | 数据规模不成立 | 15 个部门、约 70 名员工，单机 MySQL 毫秒级完成，无法体现分布式价值 | 高 |
| 5 | ETL 无增量、无质量校验 | `ETLPipeline.runEmployeeETL()` 全量抽取，只做脱敏与 `work_years` 计算，无 DQC、无失败重试 | 中 |
| 6 | 调度无依赖编排 | `ScheduledTask.scheduledETL()` 单任务 cron，无 ODS→DWD→DWS→ADS 的 DAG 依赖与执行日志 | 中 |
| 7 | 前端无效能看板 | `templates/bigdata.html` 仅展示 WordCount、部门薪资汇总等 demo 结果 | 中 |

**核心结论**：当前大数据模块是「概念演示层」，评审老师只要追问「MapReduce 的 Job 提交到哪里？Shuffle 在哪台机器？Reduce 有几个？」，就会暴露。必须补三件事：真实 MR 依赖与 Job、四层建模、百万级数据量。

**已有资产（可直接复用）**：`docker-compose.yml` 已配好 Hadoop 3.2.1（namenode + datanode）与 Hive 2.3.2（hive-server + metastore + postgresql），无需从零搭建。

## 二、目标架构

```
MySQL 业务库（employee / department / attendance / task / performance）
   │  Sqoop / JDBC 抽取
   ▼
ODS 贴源层   ods_employee / ods_attendance / ods_task      按 dt 分区，TEXTFILE 原样保留
   │  HiveQL 清洗、脱敏、维度退化
   ▼
DWD 明细层   dwd_dim_employee（拉链表 SCD2）/ dwd_fact_attendance_day / dwd_fact_task_detail
   │  HiveQL 聚合 + MapReduce 多维计算
   ▼
DWS 汇总层   dws_emp_efficiency_month（员工×时间×部门 效能宽表）/ dws_dept_efficiency_month
   │  窗口函数排名 + 回写
   ▼
ADS 应用层   ads_emp_efficiency_rank / ads_dept_efficiency_profile → MySQL → ECharts
```

## 三、P1 阶段：补齐业务事实表 + 数据扩容

### 3.1 新增三张业务源表

在 `schema-mysql.sql` 追加（同时同步 `schema-h2.sql`）：

```sql
-- 考勤事实表：效能的「投入」侧数据
CREATE TABLE attendance (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    emp_id        INT NOT NULL COMMENT '员工ID',
    work_date     DATE NOT NULL COMMENT '工作日期',
    sign_in_time  DATETIME COMMENT '签到时间',
    sign_out_time DATETIME COMMENT '签退时间',
    late_minutes  INT DEFAULT 0 COMMENT '迟到分钟数',
    overtime_hours DECIMAL(5,2) DEFAULT 0 COMMENT '加班小时数',
    leave_type    VARCHAR(10) DEFAULT '正常' COMMENT '正常/事假/病假/年假/旷工',
    work_hours    DECIMAL(5,2) DEFAULT 0 COMMENT '实际工时',

    INDEX idx_emp (emp_id), INDEX idx_date (work_date)

-- 任务工单表：效能的「产出」侧数据
CREATE TABLE task (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    emp_id        INT NOT NULL,
    task_code     VARCHAR(40) NOT NULL COMMENT '工单编号',
    task_type     VARCHAR(20) COMMENT '需求/开发/测试/运维/缺陷修复',

    create_time   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_emp (emp_id), INDEX idx_status (status)

-- 绩效结果表：效能的「结果」侧数据
CREATE TABLE performance (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    emp_id        INT NOT NULL,
    period        VARCHAR(7) NOT NULL COMMENT '考核周期 YYYY-MM',
    kpi_score     DECIMAL(5,2) COMMENT 'KPI得分',
    grade         VARCHAR(4) COMMENT 'S/A/B/C/D',
    score_by      INT COMMENT '评分人',
    create_time   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_emp_period (emp_id, period)

```

### 3.2 数据扩容生成器（关键前提）

新增 `bigdata/generator/DataGenerator.java`，按真实分布造数：

- 员工：由 70 人扩到 **5000 人**（覆盖 15 部门 × 多职级 × 多司龄段）
- 考勤：**每人 × 2 年 × 250 工作日 ≈ 250 万条**
- 任务：**每人 × 2 年 × 月均 12 单 ≈ 144 万条**
- 绩效：5000 人 × 24 月 = 12 万条

造数要求带**真实业务分布**：迟到率随司龄递减、Q4 加班强度高于 Q2、技术部任务难度分布偏高等，避免纯随机数导致分析结果无意义。生成结果落 CSV，用 `LOAD DATA INFILE` 灌 MySQL，再由 ETL 抽到 Hive。

> 这一步是「大数据」三个字成立的前提。数据量上来后，MySQL 单表聚合会明显变慢，后续性能对比实验才有说服力。

## 四、P2 阶段：Hive 四层建模（核心得分点）

### 4.1 脚本组织

新建 `src/main/resources/hive/` 目录，按层存放，由服务层按序执行：

```
hive/
  00_init_database.sql      建库 ems_dw
  01_ods_ddl.sql            ODS 建表（外部表，指向 HDFS 目录）
  02_dwd_ddl.sql            DWD 建表（ORC + 分区 + 拉链）
  03_dws_ddl.sql            DWS 宽表
  04_ads_ddl.sql            ADS 结果表
  11_ods_to_dwd.sql         清洗转换脚本
  12_dwd_to_dws.sql         多维聚合脚本
  13_dws_to_ads.sql         排名与画像脚本
```

新建 `bigdata/hive/HiveSchemaService.java`，启动时或由 `HiveController` 手动触发，按文件名顺序执行上述脚本（复用现有 `HiveRealService.getConnection()`，注意 Hive 2.3.2 不支持多语句批量执行，需按 `;` 切分逐条执行）。

### 4.2 ODS 层（贴源）

```sql
CREATE DATABASE IF NOT EXISTS ems_dw;
USE ems_dw;

CREATE EXTERNAL TABLE IF NOT EXISTS ods_attendance (
    id BIGINT, emp_id INT, work_date STRING,
    sign_in_time STRING, sign_out_time STRING,
    late_minutes INT, overtime_hours DECIMAL(5,2),
    leave_type STRING, work_hours DECIMAL(5,2)
)
PARTITIONED BY (dt STRING)
ROW FORMAT DELIMITED FIELDS TERMINATED BY '\t'
STORED AS TEXTFILE
LOCATION '/user/hive/warehouse/ems_dw/ods/attendance';
```

要点：**EXTERNAL TABLE**（删表不删数据）、**分区 dt**、**TEXTFILE 保留原始形态**——这三点写进论文能体现对 ODS 层定位的理解。

### 4.3 DWD 层（清洗 + 拉链表）

```sql
-- 员工维度拉链表（处理缓慢变化维 SCD Type 2）
CREATE TABLE IF NOT EXISTS dwd_dim_employee (
    emp_id INT, name STRING, gender STRING, age INT,
    dept_id INT, dept_name STRING,
    job_level STRING,          -- 职级：P4-P8
    seniority_level STRING,    -- 司龄分层：<1年 / 1-3年 / 3-5年 / 5年以上
    salary DECIMAL(10,2),
    start_date STRING,         -- 该版本生效日期
    end_date STRING            -- 该版本失效日期，9999-12-31 表示当前有效
)
STORED AS ORC;

-- 考勤明细（清洗 + 维度退化）
CREATE TABLE IF NOT EXISTS dwd_fact_attendance_day (
    emp_id INT, dept_id INT, dept_name STRING, work_month STRING,
    work_date STRING, is_late INT, is_leave INT, is_absent INT,
    late_minutes INT, work_hours DECIMAL(5,2), overtime_hours DECIMAL(5,2)
)
PARTITIONED BY (dt STRING)
STORED AS ORC;
```

清洗逻辑要在 `11_ods_to_dwd.sql` 中体现：**空值填充、异常值过滤**（如 work_hours > 24 视为脏数据）、**手机号脱敏**（沿用现有 ETL 的中间四位星号逻辑）、**维度退化**（把 dept_name 冗余到事实表，减少后续 Join）。

### 4.4 DWS 层（效能宽表 + 高阶 HiveQL）

这是最能体现 Hive 功底的一层，务必用上三个高级特性：

```sql
-- 员工月度效能宽表
CREATE TABLE IF NOT EXISTS dws_emp_efficiency_month (
    emp_id INT, dept_id INT, dept_name STRING,
    work_month STRING, seniority_level STRING, job_level STRING,
    attend_days INT, late_count INT, leave_count INT, absent_count INT,
    attendance_rate DECIMAL(5,4),          -- 出勤率
    avg_work_hours DECIMAL(6,2),           -- 日均工时
    overtime_hours DECIMAL(6,2),           -- 月加班总时长
    task_total INT, task_done INT, task_delayed INT,
    task_complete_rate DECIMAL(5,4),       -- 任务完成率
    ontime_rate DECIMAL(5,4),              -- 准时交付率
    avg_quality_score DECIMAL(4,2),        -- 平均质量分
    kpi_score DECIMAL(5,2),                -- KPI 得分
    efficiency_index DECIMAL(6,2),         -- 效能综合指数
    efficiency_level STRING                -- 优秀/良好/一般/待改进
)
PARTITIONED BY (dt STRING)
STORED AS ORC;
```

**得分技巧 1 —— GROUPING SETS 一次扫描出多维组合**：

```sql
INSERT OVERWRITE TABLE dws_dept_efficiency_month PARTITION (dt='${dt}')
SELECT
    dept_id, dept_name, work_month, seniority_level,
    COUNT(DISTINCT emp_id) AS emp_cnt,
    AVG(efficiency_index)  AS avg_efficiency,
    AVG(attendance_rate)   AS avg_attendance,
    AVG(task_complete_rate) AS avg_complete,
    GROUPING__ID
FROM dws_emp_efficiency_month
WHERE dt = '${dt}'
GROUP BY dept_id, dept_name, work_month, seniority_level
GROUPING SETS (
    (dept_id, dept_name, work_month),                  -- 部门×月
    (dept_id, dept_name, seniority_level),             -- 部门×司龄
    (dept_id, dept_name, work_month, seniority_level)  -- 部门×月×司龄
);
```
一次全表扫描产出三种粒度，论文里可以明确写出相比多次 UNION ALL 的代价差异。

**得分技巧 2 —— 窗口函数做排名与同环比**：

```sql
INSERT OVERWRITE TABLE ads_emp_efficiency_rank PARTITION (dt='${dt}')
SELECT emp_id, dept_name, work_month, efficiency_index,
       ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY efficiency_index DESC) AS dept_rank,
       RANK()       OVER (ORDER BY efficiency_index DESC)                      AS global_rank,
       LAG(efficiency_index, 1) OVER (PARTITION BY emp_id ORDER BY work_month) AS last_month_index,
       ROUND(efficiency_index - LAG(efficiency_index, 1) OVER (PARTITION BY emp_id ORDER BY work_month), 2) AS mom_delta
FROM dws_emp_efficiency_month
WHERE dt = '${dt}';
```

**得分技巧 3 —— 效能指数建模**。给出明确可解释的加权公式（写进论文指标定义章节）：

```
efficiency_index = 0.30 × 任务完成率×100
                 + 0.25 × KPI 得分×10
                 + 0.20 × 出勤率×100
                 + 0.15 × 准时交付率×100
                 + 0.10 × 质量评分×10
```
权重来源可做「层次分析法 AHP」或「专家打分法」简述，避免被质疑拍脑袋。

### 4.5 ADS 层（回写 MySQL）

新增 `ads_emp_efficiency_rank`、`ads_dept_efficiency_profile`，通过 JDBC 从 Hive 查出后批量写入 MySQL 同名结果表，供前端 ECharts 直接读（避免前端每次请求都触发 Hive 查询）。这一层要写清楚「为什么需要 ADS 层」：Hive 查询延迟秒级到分钟级，无法支撑前端高并发刷新。

注意：现有 `hadoop-common` 是 3.3.6，建议一并降到 3.2.1；`hive-jdbc` 保持 3.1.3 不变（Hive Client 与 Hadoop Client 版本不必强一致）。引入后务必执行 `mvn dependency:tree` 检查是否有 servlet-api / jetty 冲突导致 Spring Boot 启动失败。

### 5.2 三个必做 Job

新建包 `com.ems.bigdata.mr`：

| Job | 类 | 体现的知识点 | 论文话术 |
| --- | --- | --- | --- |
| 效能聚合 | `EmpEfficiencyMR` | 自定义 `Writable` 复合值类型 `EfficiencyWritable`（出勤/工时/任务/加班），Reduce 端加权聚合 | 「将多维指标封装为自定义 Writable，减少 Shuffle 网络传输量」 |
| 部门 TopN | `DeptTopNMR` | **二次排序**：自定义 `DeptScoreKey`（deptId + score）实现 `WritableComparable`，配 `KeyComparator` + `GroupingComparator` + `Partitioner` | 「通过二次排序在 Shuffle 阶段完成分组内排序，避免 Reduce 端全量内存排序」 |
| 维表关联 | `EmployeeJoinMR` | **Map-side Join**（`DistributedCache` 广播小维表）与 **Reduce-side Join** 两套实现对比 | 「针对维表远小于事实表的场景，采用 Map-side Join 消除 Reduce 阶段网络传输」 |

三个 Job 都要加上：

1. **Combiner**：`EmpEfficiencyMR` 设置 `job.setCombinerClass(...)`，做 Map 端本地预聚合 —— 这是论文里最经典的 Shuffle 优化点。
2. **Counter**：自定义枚举 `BAD_RECORD`、`LATE_RECORD`，统计脏数据条数并落库 —— 体现数据质量意识。
3. **多路径输入**：`MultipleInputs.addInputPath()` 同时读考勤与任务两种格式数据，用不同 Mapper 处理 —— 体现对 InputFormat 的理解。

## 七、调度、数据质量与血缘

### 7.1 DAG 编排

改造 `ScheduledTask` 为 `ETLDagScheduler`：

- 定义任务链 `ODS → DWD → DWS → ADS`，前一节点成功后才触发下一节点
- 每条链路执行记录落 `etl_job_log` 表（job_name、layer、start_time、end_time、cost_ms、input_rows、output_rows、status、error_msg）
- 失败重试 2 次，失败后中断下游并标记分区为不可用
- 保留现有 cron（每日 2:00），前端增加手动触发与「重跑某分区」按钮

### 7.2 数据质量 DQC

新增 `bigdata/quality/DataQualityChecker.java`，每层执行后校验：

1. 主键唯一性（emp_id + work_date 重复率）
2. 空值率（关键字段超阈值告警）
3. 分区完整性（当日分区记录数环比波动超 ±50% 告警）
4. 值域合法性（出勤率 ∈ [0,1]、效能指数 ∈ [0,100]）

校验结果随 Job 日志一起返回前端展示。

### 7.3 血缘

最小可用方案：在代码里维护一份 `Map<String, List<String>>` 的表级血缘（源表 → 目标表），前端画一张血缘图。不必做字段级解析，表级血缘已足够在论文中体现「数据治理意识」。

容易被追问的三个问题，提前准备：

- **Q：为什么不用 Spark？** A：MapReduce 是理解分布式计算最基础模型，本项目定位教学与工程实践结合；同时 Hive on MR 引擎与自定义 MR 可共用同一套 HDFS 存储，架构更简洁。若时间充裕可补充 Spark 版本作为性能对比第四组。
- **Q：效能指数权重怎么定的？** A：层次分析法 AHP 构造判断矩阵 + 一致性检验（CR < 0.1），或说明采用专家打分法并结合业务调研。
- **Q：数据是哪来的？** A：明确说明是在真实业务规则约束下程序化生成的仿真数据（分布参数参考真实企业考勤/绩效规律），避免被质疑数据真实性。

### B.4 需要注意的兼容问题

1. **Hive 2.3.2 对 GROUPING SETS 的支持**：脚本中已设置 `hive.new.job.grouping.set.cardinality = 64`，否则多粒度组合可能触发额外的 MapReduce Job 甚至报错。
2. **DFS 命令**：`00_init_database.sql` 中的 `DFS -mkdir -p` 在部分 HiveServer2 配置下会被拒绝执行，脚本执行器会把失败语句记录下来但继续往后执行；若建表时报目录不存在，手动在容器内执行 `hdfs dfs -mkdir -p` 即可。
3. **拉链表自读自写**：`11_ods_to_dwd.sql` 中对 `dwd_dim_employee` 同时 INSERT OVERWRITE 与 SELECT，仅非 ACID 的 ORC 表支持；若启用事务表需改写为 MERGE。
4. **大数据量写入**：`loadRows()` 使用 `INSERT INTO ... VALUES` + JDBC 批处理，11.7 万条考勤会产生较多小文件且耗时较长。做 P4 性能实验时建议改为「生成 TSV → `LOAD DATA INPATH` 入 HDFS」的方式。
5. **MyBatis Plus 分页方言**：`MyBatisPlusConfig` 中分页插件写死为 `DbType.H2`，生产环境切 MySQL 时建议改为按 profile 注入，否则分页 SQL 方言不匹配。

### C.2 三个 Job 的核心设计

**Job1 部门月度效能聚合**

1. 自定义 `EfficiencyWritable` 作为传输值，取代字符串拼接，Reduce 端无需 split 解析
2. Combiner 复用 Reducer：因为聚合是加法，满足交换律与结合律；平均值不在 Combiner 里算，而是传累计值到 Reduce 端再除
3. 自定义 `DeptPartitioner` 按 deptId 取模：默认 HashPartitioner 会把 month 混进 hashCode，同部门散到不同 Reducer
4. Counter 做 DQC：脏数据不丢弃，计数后修正（工时截断到 0~24），作业结束可从 Counters 读出质量报告

**Job2 部门 TopN（二次排序）**

由三个可插拔组件共同完成，缺一不可：

1. `ScorePartitioner` 按部门分桶
2. `ScoreSortComparator` 部门升序 + 分数降序（直接比较序列化字节，跳过反序列化）
3. `DeptGroupComparator` 只按部门分组，使同部门记录进入同一次 reduce() 调用

Reducer 用 `HashSet` 去重 emp_id：因已按分数降序排列，首次出现即该员工"最佳月度表现"，取满 N 个即 break，内存占用 O(N) 与部门人数无关。

**Job3 维表关联**

1. Map-side：维表通过 `job.addCacheFile` 广播到每个 Map，setup 读入 HashMap，`setNumReduceTasks(0)`，无 Shuffle
2. Reduce-side：`MultipleInputs` 接入两种输入源各用不同 Mapper 打 F/D 标签，Reducer 拆分后关联
3. 两者输出格式一致，可直接做结果一致性校验与性能对比

### C.5 Windows 本地运行踩坑记录

1. **hadoop.dll 版本必须匹配**：本机 `HADOOP_HOME=D:\hadoop\hadoop-3.4.3`，PATH 指向其 bin，但目录里只有 winutils.exe 没有 hadoop.dll；`D:\hadoop\bin\hadoop.dll` 是 2.x 版本，缺 `anchorNative` 符号，会导致 `UnsatisfiedLinkError`。已下载 3.3.5 版本的 hadoop.dll 放到 `D:\hadoop\hadoop-3.4.3\bin\`，PATH 已覆盖，无需再手动指定 `java.library.path`。
2. **JDK 17 模块封装**：Hadoop 3.3.x 官方支持到 JDK 11，JDK 17 下需加
   `--add-opens java.base/java.lang=ALL-UNNAMED --add-opens java.base/java.util=ALL-UNNAMED`。
   `MrJobService` 已通过 `mapreduce.map/reduce.java.opts` 为容器自动注入；Spring Boot 驱动进程仍需在启动命令里手动加这两个参数。
3. **跨机器访问**：从宿主机提交作业到 docker 集群时，NameNode 返回的 datanode 主机名（如 `datanode`）宿主机无法解析。解决办法二选一：把 Spring Boot 应用也接入 `hadoop-net` 容器网络；或在 hosts 里映射并暴露端口。毕设演示更推荐前者。
4. **切换到 YARN 只需三步**：`docker-compose up -d` 启动新增的 resourcemanager/nodemanager → `bigdata.mr.framework: yarn` → `bigdata.mr.fs-default-fs: hdfs://localhost:9000`，随后在 `localhost:8088` 可看到作业记录，截图即可用于论文。
